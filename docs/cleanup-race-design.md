# 清理竞态：边界与后续架构方案

状态：技术方案，尚未实现。评估日期：2026-10-21。对应审计项：FCP-01。

本轮保留现有清理实现。现有快照复验、路径白名单、授权与卷检查不能消除最后一次复验到 `FileManager.trashItem` 之间的路径竞态。下面的隔离方案需要恢复界面、持久化协议和外接盘验证，不能作为几个额外 `stat` 调用直接加入现有执行器。

## 当前行为及剩余风险

[`CleanupSafety`](<../FCP Cleaner/FCP Cleaner/Services/CleanupSafety.swift>) 对照最初扫描的祖先和整个候选树，检查设备号、inode、创建时间、mtime、ctime、大小、链接数和成员。它拒绝检测到的路径替换、符号链接、Finder 别名、跨卷和内容元数据变化。

[`CleanupExecutor`](<../FCP Cleaner/FCP Cleaner/Services/CleanupExecutor.swift>) 在授权和 Final Cut Pro 检查的 `await` 返回后再次检查卷及完整快照，随后同步调用唯一的真实移动接口。两者之间没有应用自己的挂起点，但操作系统仍可调度其他进程；系统移动 API 内部也可能等待或重新解析路径。

例如，原始扫描确认缓存目录 A；最终复验通过后，另一进程把 A 改名，并把目录 B 放到原路径。按原 URL 发起的废纸篓操作可能移动 B。成功返回只证明系统移动成功，不能证明移动对象仍为 A。现有测试覆盖发生在复验之前和授权等待期间的变化，不能证明此最终窗口不存在。

因此，FCP-01 本轮结论为**已完成评估，残余竞态仍存在**。保持资源库和磁盘稳定、退出 Final Cut Pro 及其他写入任务仍是使用条件。元数据相同也不能证明文件内容字节未变；当前扫描不计算内容哈希。

## 为什么小改动不能提供原子保证

| 方法 | 能改善的情况 | 不能保证的部分 |
| --- | --- | --- |
| 再次 `lstat` / 缩短代码间隔 | 检出更多已经发生的变化 | 检查结束后仍可替换路径 |
| `openat`、`O_NOFOLLOW`、`fstat`、持有目录 FD | 逐级不跟随链接、稳定引用已打开对象并核对身份 | `trashItem` 接收 URL，不接受该 FD 或期望 inode，仍会按路径定位 |
| `O_NOFOLLOW_ANY` | 在支持的系统上拒绝该次 `open` 解析中的链接 | 不会约束后续 Foundation 移动操作 |
| `NSFileCoordinator` | 协调采用文件协调协议的访问者 | 不能锁住不参与协调的进程；不能据此声称阻止恶意替换 |
| `renameatx_np` + `RENAME_EXCL` | 相对固定父目录进行同卷、不覆盖的名称移动 | 不提供“仅当源 inode 等于预期值时移动”；源名称仍可在调用前被替换 |

Apple 的 [`trashItem` 文档](https://developer.apple.com/documentation/foundation/filemanager/trashitem(at:resultingitemurl:)) 定义的是 URL 移动和返回位置。公开接口没有接受原始身份快照的参数。上表对组合操作安全性的判断是据此及系统调用语义作出的工程推论，不是 Apple 对此组合提供的保证。[文件协调文档](https://developer.apple.com/documentation/foundation/nsfilecoordinator) 说明其协调对象为 file presenters。

## 可原型验证的隔离架构

目标是将“改变原位置”与“允许进入废纸篓”拆为可恢复阶段：先捕获名称，再确认捕获的对象，确认失败时不送入废纸篓。它能缩小原路径替换造成的错误移动范围，**仍不能直接满足任意同一用户身份的恶意进程下的原子身份保证**，也可能短暂隔离被替换的非缓存目录。只有明确接受这个边界并满足以下验收条件后，才可考虑实现。

### 1. 授权、描述符和能力预检

- 保持现有精确路径白名单、原始快照、FCP 检查及授权范围，不因为隔离而放宽任何一项。
- 从已授权父目录开始，逐组件使用不跟随链接的 `openat` 打开目录，以 `fstat` 核对设备、inode、创建时间和类型，持有操作需要的 FD；枚举和后续检查尽可能相对这些 FD 完成。每个失败都中止，不回退到跟随链接的绝对路径操作。
- 新目录创建会改变祖先元数据。隔离目录必须在创建扫描快照前准备，或作为单独可验证的受控变更建模；不能在用户确认后直接刷新整份快照。现有批次的渲染/分析执行顺序也必须重新验证。
- 隔离位置必须位于同一设备并在已授权范围内。以目录 FD 核对它的真实身份，拒绝预先存在的链接和不符合所有权/权限条件的条目。每项使用独立随机操作 ID 和不复用的名称。
- 预先确认文件系统支持所需的无覆盖操作。`RENAME_EXCL` 不支持、`EXDEV`、只读、断盘或属性不明时拒绝隔离；不得改用复制后删除，也不得使用普通 `rename` 覆盖已有目录。
- `0700` 和随机名称可以防止其他用户或误碰，不能防御具有同一 UID、能够访问该卷的恶意进程。不得把“私有隔离目录”当作该威胁模型下的安全边界。

### 2. 在每次数据移动前落盘计划

新增版本化恢复记录，至少包含操作 ID、授权书签引用、卷标识、设备及对象身份、原始相对路径、隔离相对路径、当前阶段和上次系统调用结果。真实路径和书签只保存在本地受保护日志中，不加入遥测、公开报告或源码。

先写临时记录，完成文件同步，再原子替换正式记录，并验证目录项持久化策略。只有恢复记录成功落盘后才能修改文件位置。外接盘与内部日志位于不同文件系统，不能假设它们存在跨卷事务；各阶段必须能够通过实际对象状态重建结果。

### 3. 原子捕获名称，随后验证捕获对象

使用持有的源父目录 FD 和隔离父目录 FD，通过单次 `renameatx_np` 加 `RENAME_EXCL` 移动源名称；结合经过目标系统验证的无链接/目录边界约束。此调用捕获的是调用时该名称所指的条目，不是经过原子 compare-inode 的对象。

捕获后立即以不跟随链接的方式核对隔离对象。必须确认它与捕获前持有的 FD 及原始快照身份一致，并检查完整树、类型和设备。目录改名本身可能改变 ctime 等元数据；需明确区分可证明由本操作引起的变化和外部变化，不能简单忽略全部 ctime 或重新接受整个对象树为新基准。无法解释的变化按验证失败处理。

验证失败时不调用 `trashItem`，也不递归删除隔离内容。进入下述无覆盖恢复流程。隔离成功本身不记为清理完成，容量也不计入已完成值。

### 4. 废纸篓提交与恢复

捕获验证成功、恢复记录更新成功且授权仍有效后，才允许针对隔离位置调用系统废纸篓 API。持有 FD 期间仍需确认路径对应关系；如果同一 UID 进程能改写隔离位置，这里仍存在新的路径窗口。没有经过证明的不可被该进程替换的隔离边界时，不得宣称完全消除恶意竞态。不要为获取这种边界直接引入提权 helper。

系统成功返回后，将返回的废纸篓 URL 与实际结果写入日志；记录失败时停止批次并保留“可能已移动”的恢复状态。失败或抛错时检查源、隔离、返回位置的身份，不能仅凭异常就假定完全未移动，更不能自动重复发送废纸篓操作。

恢复只使用经过能力验证的无覆盖原子移动：

- 原始父目录、卷及授权仍匹配，且原名称空闲：尝试 `RENAME_EXCL` 还原，并核对还原身份；存在冲突时停止。
- 原名称被新目录或文件占用：保留隔离对象及恢复记录，由用户选择另一个已授权且空闲的位置。绝不覆盖、合并或删除占位对象。
- 断盘、授权丢失、无法确定对象位置：保留记录，停止进一步修改；同一卷重新连接并重新授权后再核对。路径相同但卷身份不同不算原卷。
- 批次取消：等待当前系统调用结束，落盘该项的真实阶段，停止下一项；不在无法确认的状态下自动回滚。

### 5. 崩溃后的保守重建

| 最后持久化阶段 | 重启后的处理 |
| --- | --- |
| `planned` / `captureRequested` | 核对原位置和隔离位置。原对象仍在原处且隔离为空可判为未捕获；隔离存在匹配对象则进入恢复待确认 |
| `captured` / `capturedVerified` | 保留对象，展示待恢复项；不自动继续清理或认定可安全删除 |
| `trashRequested` | 结果可能不明确。核对隔离位置及已知废纸篓位置；不通过同名条目猜测，不重复 trash |
| `trashed` | 展示已记录的真实结果；路径或对象无法核实时明确标记恢复状态未知 |
| `restoreRequested` | 核对两个位置的对象身份。只有唯一且匹配的对象可确认恢复；双位置、冲突或均缺失均需人工处理 |

设备号可能在重挂载后改变，inode 也可能重用；不能以单一字段认领对象。恢复必须结合重新授权得到的卷身份、对象身份、原始记录及现场状态。证据不足时保存数据和日志、请求人工核对。恢复记录损坏、缺失或版本未知时不进行猜测性清理。

## Finder、沙盒与外接盘验收门槛

从隔离目录送入废纸篓后，Finder 的“放回原处”可能指向隔离目录。公开 `trashItem` 接口没有指定另一个原始恢复位置的参数，不能假设系统会保留隔离之前的位置。原型必须实测此行为；若不能保持现有恢复体验，必须先设计并验证应用内无覆盖恢复，向用户明确恢复位置。不要写入未公开的废纸篓元数据来模拟 Finder 行为。

必须在启用实际 App Sandbox、`user-selected.read-write` 授权和安全作用域书签的签名应用中验证整个流程。命令行单元测试通过不等于沙盒授权可用。移出授权目录、隔离目录创建失败、书签失效及重启后恢复均须拒绝越权操作。

最低 macOS 版本、当前系统、内置 APFS、真实外接 APFS、大小写敏感卷及其他拟支持格式应分别验收；不支持原子无覆盖能力的格式继续拒绝。还需覆盖卷空间耗尽、磁盘拔出/重接、挂载名称冲突、休眠及中途权限改变。所有测试仅使用明确创建的合成资源库，不接触用户现有媒体，也不清空废纸篓。

## 测试与上线条件

保留并运行现有 `CleanupSafetyTests`、`CleanupExecutorTests`、`CleanupVolumeCheckerTests` 和 `ExternalDiskCleanupTests`。当前测试已验证每层及后代链接拒绝、对象/祖先/成员变更、授权等待期间变化、FCP/卷拒绝、取消语义、日志失败，以及真实合成缓存移动时受保护文件不变。

原型还必须增加可确定调度点的故障注入测试：最终复验前后替换目标和每级祖先；捕获前换入符号链接、普通目录或受保护合成媒体；捕获后修改隔离入口；每个记录/系统调用边界崩溃；恢复时原名称被抢占；trash 成功而最终日志失败；断盘后同路径挂载另一卷。每个用例应断言实际对象位置和内容、没有覆盖或永久删除、没有错误完成记录，以及下次启动的恢复结果。

如果仍不能证明隔离入口不被威胁进程替换，或者无法保证失败后的可恢复性与 Finder/沙盒体验，就不替换当前执行器。完整的原子“验证身份并送入系统废纸篓”需要系统支持或进一步架构研究，不能通过新增模拟测试得出保证。

系统调用语义依据：Apple [`open(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/open.2.html)、[`rename(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/rename.2.html)，以及当前 Xcode SDK 随附的 `open(2)` / `rename(2)` 手册中 `openat`、`renameatx_np`、`RENAME_EXCL` 和无链接标志说明。归档网页未包含所有新标志；实现前须核对部署版本的 SDK 和文件系统能力。
